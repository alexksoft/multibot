.you can automate cookie refreshing so you don&#39;t have to manually use Cookie-Editor every month. Because Facebook uses strict bot-detection, the safest way to do this is by reusing a dedicated browser profile rather than logging in from scratch repeatedly.

1. Use a Persistent Browser Profile (Recommended)

Instead of exporting and importing JSON cookies, let your script point directly to a dedicated Chrome or Chromium user data folder on your Windows laptop.
• How it works: You log into Facebook once inside a separate browser profile (for example, C:\fb_scraper_profile). Playwright or Selenium then launches using that exact folder path (launch_persistent_context in Playwright).
• Why it stays logged in: Just like your normal daily browser, Chrome automatically refreshes session tokens in the background whenever the scraper visits Facebook.
• Safety benefit: Because the browser keeps the exact same device fingerprint, local storage, and cache, Facebook rarely flags the session as suspicious.

2. Read Cookies Directly from Your Browser

If you prefer keeping your current fb_session.json architecture, you can run a small local script to pull fresh cookies straight from your installed browser&#39;s SQLite database.
• How it works: Python libraries like browser-cookie3 or rookiepy read your local Chrome or Edge cookie store and extract the active facebook.com cookies into fb_session.json.
• Trade-off: Modern Windows versions encrypt browser cookies using App-Bound Encryption. Reading them externally often requires closing the browser first or running with specific system permissions, making a persistent profile much more reliable.

3. Automated Login Fallback (Higher Risk)

You can program your script to detect when it gets redirected to the login screen and automatically type in your email, password, and a 2FA code generated via pyotp.
• Why to use caution: Automated logins from headless browsers frequently trigger Facebook security checkpoints, CAPTCHAs, or temporary account locks.
• Best practice: Only use automated login as a last-resort backup if a persistent browser profile gets logged out.

Стовідсоткової гарантії безперебійної роботи на роки наперед при парсингу Facebook не існує, оскільки платформа постійно змінює верстку та алгоритми захисту від ботів. Проте перехід на постійний профіль браузера (Persistent Profile) робить систему максимально стабільною — вона може працювати місяцями без вашого втручання, якщо правильно захистити її від технічних «зависань».
Ось де ховаються головні ризики збоїв і як їх закрити, щоб система не падала:

1. Де система може «зависнути» або впасти

• Блокування профілю (Lock-файл): Якщо скрипт впаде з помилкою і не закриє браузер коректно, у папці профілю залишиться файл SingletonLock. Наступний запуск просто зависне або видасть помилку, бо вважатиме, що браузер досі відкритий.
• Витік пам&#39;яті (Memory Leak): Браузери на базі Chromium при тривалому скролінгу важких сторінок Facebook швидко з&#39;їдають оперативну пам&#39;ять, через що процес може намертво зависнути.
• Перевірки безпеки (Checkpoints): Навіть у постійному профілі Facebook раз на кілька місяців може викинути вікно «Підтвердіть, що це ви» або капчу, якщо поведінка здасться занадто регулярною.
• Зміна верстки (DOM): Facebook регулярно оновлює назви CSS-класів. Тоді браузер не падає, але парсер починає повертати порожні списки постів.

2. Як зробити систему максимально «невбиваною»

Щоб local_api.py не доводилося перезапускати вручну, у код закладають кілька запобіжників:
• Жорсткі таймаути (Timeouts): Кожен запит від сервера Oracle повинен мати суворий ліміт часу (наприклад, 60–90 секунд). Якщо сторінка зависла, скрипт примусово вбиває процес браузера (browser.close() або через taskkill), звільняє пам&#39;ять і повертає помилку, щоб наступний цикл пройшов чисто.
• Очищення Lock-файлів перед стартом: Перед кожним відкриттям профілю скрипт перевіряє, чи немає завислих процесів цього профілю, і прибирає залишкові файли блокування.
• Алерт у Telegram при збої: Замість того, щоб гадати, чи працює парсер, у local_api.py додається перевірка: якщо скрипт бачить сторінку входу (/login) або отримує 0 постів тричі поспіль, він одразу надсилає вам повідомлення в Telegram.
• Робота через Tailscale та режим сну Windows: Головна причина «падінь» при запуску з домашнього ноутбука — це перехід Windows у режим сну (Sleep), коли ви закриваєте кришку або довго не чіпаєте мишку. Для стабільної роботи в налаштуваннях живлення Windows потрібно вимкнути перехід у сон при живленні від мережі.
